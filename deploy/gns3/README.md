# GNS3 labs for MANGO VPN

This directory builds two GNS3 projects that rehearse MANGO VPN's deployment
shapes on one host. Both are generated by an automated kit: image builds, a
cloud-init seed for the Ubuntu VMs, and a stdlib-only Python provisioner.

| Lab | GNS3 project | Rehearses | Tutorial |
| --- | --- | --- | --- |
| Lab 1 | `Mango-VPN-TrackB-C1` | Track B mock cloud, and Track C Part C1 (one Ubuntu 24.04 VM running the Compose stack) | [`02-track-b-gns3-mock-cloud.md`](../../docs/tutorial/02-track-b-gns3-mock-cloud.md), [`03-track-c-cloud-deployment.md`](../../docs/tutorial/03-track-c-cloud-deployment.md) |
| Lab 2 | `Mango-VPN-AWS-C2` | Track C Part C2 managed AWS VPC (`10.50.0.0/16`), mirroring [`deploy/aws-managed/template.yaml`](../aws-managed/template.yaml) | [`03-track-c-cloud-deployment.md`](../../docs/tutorial/03-track-c-cloud-deployment.md) |

> **Run one lab at a time.** Both projects bridge their `Cloud` node to the same
> host bridge, `virbr-gns3`, and the host uses the same client-LAN address
> (`192.168.50.10`) for either one. Stop one project before you start the other.

> **`sim-fortigate` and `sim-cisco` are REST control-plane simulators.** They
> are `Mango Appliance Sim` nodes that answer a token-authenticated,
> Fortinet- or Cisco-style management API on `:8443`, which the gateway calls.
> They are **not** FortiGate or Cisco data planes. They forward no packets.
> All forwarding is done by the Linux routers and the WireGuard gateway.

---

## 1. Prerequisites

- A GNS3 controller with KVM/QEMU and Docker. The provisioner reads
  `GNS3_URL`, `GNS3_USERNAME`, and `GNS3_PASSWORD`. If they are unset, it falls
  back to `~/.config/GNS3/3.1/gns3_gui.conf`.
- Host tools: `xorriso`, `qemu-img`, and `ssh-keygen` (for
  `build-control-seed.sh`), and Python 3. `wg` is optional: without it the
  provisioner generates the X25519 keypair with `openssl`.
- The Ubuntu 24.04 cloud image at
  `~/GNS3/images/QEMU/ubuntu-24.04-cloudimg-amd64.qcow2`.
- A `virbr-gns3` bridge on the host (for example, a libvirt network). The
  `Cloud` node binds to it, and `host-client-lan.sh` fails without it.
- The GNS3 appliance templates below. The provisioner stops with
  `GNS3 templates missing: ...` if any is absent:
  - Standard: `Cloud`, `Ethernet switch`, `NAT`
  - VMs: `Windows 11 Edu/Pro (Ready VM)`, `Security & Pentest Desktop (Kali Linux)`,
    `Windows Server 2025 (Ready VM)`, `Windows Server 2022 Uni (Ready VM)`
  - Service templates: `Uptime & Synthetics (Uptime Kuma)`,
    `Git & CI/CD Platform (Gitea)`, `PostgreSQL 16`, `AWS Cloud Emulator (LocalStack)`,
    `Container Registry (Registry)` (`provision-gns3-lab.py` pins LocalStack to
    the community `localstack/localstack:3.8.1` release while preserving its icon
    and name format, because `latest` requires `LOCALSTACK_AUTH_TOKEN`).

## 2. Quick Start (automated kit)

Run these from the repository root:

```sh
# 1. Build the Docker images behind the Docker nodes (16 images)
./deploy/gns3/build-images.sh

# 2. Create the 25 GB Ubuntu disk, the SSH lab key, and the two cloud-init seed ISOs
./deploy/gns3/build-control-seed.sh

# 3. Create the GNS3 projects, one lab at a time
python3 deploy/gns3/provision-gns3-lab.py --lab c1 --recreate
python3 deploy/gns3/provision-gns3-lab.py --lab c2 --recreate   # only after stopping Lab 1

# 4. Client LAN bridge helper (host side, needs root)
sudo ./deploy/gns3/host-client-lan.sh up       # host = 192.168.50.10/24, route 203.0.113.0/24 via 192.168.50.1
sudo ./deploy/gns3/host-client-lan.sh status
sudo ./deploy/gns3/host-client-lan.sh down
```

What each step produces:

- **`build-images.sh`** builds `mango-gns3-router`, `-target`, `-harness`,
  `-coredns`, `-probe`, `-appliance-sim`, `-alb-caddy`, `-openbao`,
  `-prometheus`, `-loki`, `-grafana`, `-rustfs`, `-gateway` (from
  `Sobree/vpn-daemon`), `-api`, `-ecs-api`, and `-portal`, all tagged `:local`.
  The portal is built with `VITE_API_URL=https://vpn.mango.lab`.
- **`build-control-seed.sh`** writes to `~/GNS3/images/QEMU/`:
  - `mango-ubuntu-24.04-25g.qcow2`, the 25 GB base disk for the Ubuntu VMs
  - `ubuntu-control-c1-seed.iso` and `ec2-wg-gateway-c2-seed.iso`
  - `deploy/gns3/.local/lab_ed25519` and `.pub`, the SSH lab key (created once)

  Each VM gets a `lab` user with passwordless sudo and the `docker` group, key-only
  SSH, and Docker, WireGuard tools, nftables, and Node.js installed. The seed also
  installs a `mango-vpn-return-route.timer`. Every 10 seconds it runs
  `ip route replace 10.13.13.0/24 via 172.29.0.10` once the `172.29.0.0/24` Docker
  bridge exists. That is the no-NAT return path from Track B section 2.1, so the
  automated labs apply it without a manual step.
- **`provision-gns3-lab.py`** writes `deploy/gns3/.local/lab-secrets.json`
  (generated secrets and the WireGuard keypair, mode `0600`), `c1.env`, and
  `c2-gateway.env` into `.local/` (directory mode `0700`). It then upserts the
  Docker and QEMU templates and creates the project.
  - Before `--recreate` or `--start-core`, it closes any other open `Mango-VPN-*`
    project so only one lab claims `virbr-gns3` and `virbr0`.
  - `--recreate` deletes any existing project with the same name first. Its
    nodes and links are lost, so export anything you want to keep first.
  - Without `--start-core`, nodes are created but not started.
  - `--start-core` is idempotent on an existing project: it opens the project
    and starts only the non-stopped core nodes without recreating objects,
    leaving the four heavy VMs stopped.
  - `host-bridge` (`Cloud`) binds `virbr-gns3` via an explicit bridged TAP
    (`mango-lan0`, `type: "tap"`, `bridge: "virbr-gns3"`) instead of GNS3's
    auto-allocated `gns3tap0-0`, preventing collisions with `oob-nat` (`NAT` on
    `virbr0`).
  - Both Ubuntu QEMU templates pass
    `-global virtio-net-pci.csum=off -global virtio-net-pci.gso=off -global virtio-net-pci.guest_csum=off`
    so the guests compute full software L4 checksums across GNS3 uBridge/TAP
    and host `nf_conntrack` + `UFW` do not drop `virbr0` OOB SSH/DNS as `INVALID`.
  - `--lab all` provisions both projects in one run. Both still share
    `virbr-gns3`, so do not start both at once.

### Heavy VMs are pre-wired but stopped

`client-win11`, `kali-wan`, `win2025-admin`, and `win2022-staff` are linked into
their segments but are never started by `--start-core`. Start each one from the
GNS3 GUI only when you need it. They are large and slow to boot.

## 3. Lab 1: `Mango-VPN-TrackB-C1`

Track B mock cloud plus Track C Part C1 (`26` nodes, `27` links, `6` zone
drawings). The Ubuntu control VM runs the Compose
stack behind Caddy, the WireGuard gateway, and the appliance simulators. Private
zones sit behind a VPC router, and the WAN router refuses to route them.

Traffic path: `Client LAN -> wan-router -> ubuntu-control (vpn-gateway) -> vpc-router -> zones`.

`ubuntu-control` eth2 is a NAT-node uplink (DHCP) for package and image pulls.
Its cloud-init routes are `10.99.0.0/24`, `10.20.0.0/16`, and `10.30.0.0/24` via
`172.28.0.1`, and `192.168.50.0/24` via `203.0.113.1`.

### Routing and firewall rules that define the lab

- **`wan-router`** has no routes to `10.13.13.0/24` or the private zones. A probe
  to a private target must fail before the tunnel is up.
- **`wan-router` (`table inet sg_wan`, `policy drop`)** allows ICMP, DNS (`53`
  to `203.0.113.53`), HTTP/HTTPS (`80`/`443` to `203.0.113.10`), WireGuard
  (`51820/udp` to `203.0.113.10` and `203.0.113.20`), appliance simulator ports
  (`443`/`8443` to `.21`/`.22`), and management SSH strictly from the host
  bridge IP (`192.168.50.10 -> 203.0.113.10:22`). Other client-LAN nodes such
  as `test-harness` and `client-win11` remain blocked from WAN SSH.
- **`vpc-router`** adds `10.13.13.0/24 via 172.28.0.2` (the tunnel return path). It
  has no route to `192.168.50.0/24`, which preserves client-LAN isolation.
- **`sim-fortigate` and `sim-cisco`** are on the public WAN and the transit
  segment. The gateway reaches them on the transit side.

| --- | --- |

| Route 53 public DNS | `dns-route53` (CoreDNS, `Corefile.c2`, zones `mango.lab` and `aws.lab`) |
| Internet gateway, Elastic IP NAT, security groups | `aws-igw-router` nftables tables `aws_nat` (DNAT and SNAT) and `aws_sg` (forward chain) |
| `VpnReturnRoute` (`10.13.13.0/24` to the gateway instance) | `aws-igw-router`: `10.13.13.0/24 via 10.50.1.20` |
| Public subnet, ALB | `alb-ingress` (Caddy, `tls internal`, `10.50.1.10`) |
| WireGuard EC2 gateway (`SourceDestCheck: false`) | `ec2-wg-gateway` (`10.50.1.20`) |
| Private subnets: ECS API and portal, RDS | `ecs-api` (`10.50.10.11`), `ecs-portal` (`10.50.10.12`), `rds-postgres` (`10.50.10.20`, `PGDATA=/var/lib/postgresql/data/pgdata`) |
| AWS platform subnet | `aws-localstack` (`localstack/localstack:3.8.1`), `aws-ecr`, `aws-prometheus`, `aws-loki`, `aws-grafana`, `aws-rustfs` (`10.50.30.0/24`) |
| Private target zones | `vpc-router` and the three target nodes |

### Address plan

| Segment | Node and interface | Address |
| --- | --- | --- |
| Client LAN `192.168.50.0/24` | Host via `host-bridge`, `test-harness`, `wan-router` eth0 | `192.168.50.10`, `192.168.50.20`, `192.168.50.1` |

| AWS public `10.50.1.0/24` | `aws-igw-router` eth1 / `alb-ingress` / `ec2-wg-gateway` | `10.50.1.1` / `10.50.1.10` / `10.50.1.20` |

| | `aws-grafana` / `aws-rustfs` | `10.50.30.32` / `10.50.30.40` |

| Private targets | `vpc-router` eth1, eth2, eth3 | `10.99.0.1`, `10.20.0.1`, `10.30.0.1` |
| | `target-admin`, `target-staff`, `target-client` | `10.99.0.10`, `10.20.0.10`, `10.30.0.10` |
| WireGuard `10.13.13.0/24` | `vpn-gateway` in the `ec2-wg-gateway` Compose stack | `10.13.13.1` (gateway `wg0`) |

### Routing and firewall rules

- **Public ingress** is limited to TCP `80`/`443` to `10.50.1.10` (ALB) and UDP
  `51820` to `10.50.1.20` (WireGuard), through DNAT. `vpn.mango.lab` resolves to
  `203.0.113.10` and `wg.mango.lab` to `203.0.113.20`. Although `wan-router`
  permits `192.168.50.10 -> 203.0.113.10:22` for Lab 1, in Lab 2
  `203.0.113.10` is `aws-igw-router`'s ALB EIP (`aws_nat` only DNATs `80`/`443`
  and `aws_sg` drops `:22`), so Lab 2 keeps no public SSH path.
- **East-west flows** are allowed by `aws_sg` only: ALB to `ecs-api:4000` and
  `ecs-portal:3000`, `ecs-api` to `rds-postgres:5432`, and `ecs-api` to the
  gateway daemon at `10.50.1.20:50051`.
- **Tunnel return path**: `aws-igw-router` routes `10.13.13.0/24` via `10.50.1.20`
  (the gateway). `vpc-router` routes `10.50.0.0/16` via `172.28.0.2`
  (`ENABLE_AWS_VPC_ROUTE=true`).
- **Client LAN**: `aws-igw-router` routes `192.168.50.0/24` via `203.0.113.1` and
  uses the WAN default route. Its `aws_sg` rules accept `10.13.13.0/24` into the
  private zones and the platform subnet only, so the zones are reachable only
  from the WireGuard subnet.

## 5. Launch the control planes

### 5.1 Lab 1: Compose stack on `ubuntu-control`

1. Start the Lab 1 project, either in the GUI or with
   `provision-gns3-lab.py --lab c1 --start-core`.
2. Bring up the host side of the client LAN:
   `sudo ./deploy/gns3/host-client-lan.sh up`. This gives you a route to
   `203.0.113.10`.
3. Wait for cloud-init on the VM:

   ```sh
   KEY=deploy/gns3/.local/lab_ed25519
   ssh -i "$KEY" lab@203.0.113.10 'cloud-init status --wait'
   ```

4. Copy the repository to the VM. `rsync` also copies `deploy/gns3/.local/c1.env`:

   ```sh
   rsync -az --exclude node_modules --exclude .git -e "ssh -i $KEY" \
     ./ lab@203.0.113.10:Mango_VPN_Trainee/
   ```

5. Start the stack with the generated env file:

   ```sh
   ssh -i "$KEY" lab@203.0.113.10
   cd ~/Mango_VPN_Trainee
   docker compose -f deploy/gns3/docker-compose.gns3.yml --env-file deploy/gns3/.local/c1.env up -d --build
   docker compose -f deploy/gns3/docker-compose.gns3.yml ps
   ```

`c1.env` sets `WG_SERVER_ENDPOINT=203.0.113.10:51820`, `CORS_ORIGIN` and
`VITE_API_URL` set to `https://vpn.mango.lab`, and the FortiGate and Cisco REST
URLs and tokens (`http://172.28.0.21:8443`, `http://172.28.0.22:8443`). Its
`DATABASE_URL` points at `localhost:15432`, which is for host-side seeding. Compose
gives the `api` container its own URL on the Docker network. PostgreSQL is
published only on `127.0.0.1:15432`.

### 5.2 Lab 2: WireGuard gateway on `ec2-wg-gateway`

The seed already wrote `/opt/mango-gateway/docker-compose.yml`. It loads the
`mango-gns3-gateway:local` image and reads `/opt/mango-gateway/.env` as its
`env_file`. The gateway needs no build on the VM.

1. Start the Lab 2 project, and wait for cloud-init on `ec2-wg-gateway`.
2. Lab 2 has no public SSH path. Use the out-of-band `virbr0` DHCP address on
   the second NIC (`ens1` under `virtio-net-pci`, shown by `ip -br addr` in the
   GNS3 console or `/var/lib/libvirt/dnsmasq/virbr0.status` on the host), then set it:

   ```sh
   OOB=<oob-dhcp-address>
   KEY=deploy/gns3/.local/lab_ed25519
   ```

3. Load the gateway image from the host (the VM has no registry access):

   ```sh
   docker save mango-gns3-gateway:local | ssh -i "$KEY" lab@"$OOB" 'docker load'
   ```

4. Install the gateway env file, readable by the `lab` user that runs Compose:

   ```sh
   scp -i "$KEY" deploy/gns3/.local/c2-gateway.env lab@"$OOB":/tmp/c2-gateway.env
   ssh -i "$KEY" lab@"$OOB" \
     'sudo install -m 600 -o lab -g lab /tmp/c2-gateway.env /opt/mango-gateway/.env && rm /tmp/c2-gateway.env'
   ```

5. Start the gateway and check it:

   ```sh
   ssh -i "$KEY" lab@"$OOB" 'cd /opt/mango-gateway && docker compose up -d && docker compose ps'
   ssh -i "$KEY" lab@"$OOB" 'cd /opt/mango-gateway && docker compose exec vpn-gateway wg show'
   ```

   The `inet mango_vpn` nftables table lives inside the gateway container's
   namespace, so inspect it with `docker compose exec vpn-gateway nft list table inet mango_vpn`.
   It is not visible from the VM host.

Its listen addresses are `51820/udp` and `10.50.1.20:50051`, matching
`VPN_DAEMON_URL=http://10.50.1.20:50051` in the `ecs-api` node. The VM host's
`10.13.13.0/24` return timer applies here as well, so `wg show` should list peers
on `wg0` once clients connect.

### 5.3 Lab 2: application nodes

`ecs-api`, `ecs-portal`, `rds-postgres`, `alb-ingress`, and the platform nodes
are Docker nodes. They are not in the stopped list, so `--start-core` starts them.
Starting them in the GUI works too. `ecs-api` runs Prisma migrations on startup,
which must finish before you seed.

## 6. Seed the first ADMIN and the Track B policies

Seed after the API has started, and before any client connects. The gateway reads
the enabled policies for the user's role at connect time.

### Lab 1 (on `ubuntu-control`)

```sh
cd ~/Mango_VPN_Trainee
npm install
npm run db:generate
set -a; . deploy/gns3/.local/c1.env; set +a     # DATABASE_URL -> localhost:15432
SEED_ADMIN_USERNAME=admin SEED_ADMIN_PASSWORD='<Choose-12+-Char-Password>' npm run db:seed
npm run db:seed:test-targets
```

Expected output: `Seeded roles [ADMIN, STAFF, CLIENT] and ADMIN user "admin".`,
then `Seeded 12 Track B VPN policies.`

### Lab 2 (in the `ecs-api` container, on the GNS3 host)

The `ecs-api` image is built from `mango-gns3-api`, so it ships the same compiled
seeders at `/app/Rain/admin/dist`. Its `DATABASE_URL` points at `rds-postgres`:

```sh
CID=$(docker ps --filter ancestor=mango-gns3-ecs-api:local --format '{{.ID}}' | head -n1)
docker exec -e SEED_ADMIN_USERNAME=admin -e SEED_ADMIN_PASSWORD='<Choose-12+-Char-Password>' \
  "$CID" node Rain/admin/dist/seed.js
docker exec "$CID" node Rain/admin/dist/seed-test-targets.js
```

Use a password of at least 12 characters.

## 7. Connect and verify

Both labs use the same client procedure as Track B sections B4 to B6 in
[`02-track-b-gns3-mock-cloud.md`](../../docs/tutorial/02-track-b-gns3-mock-cloud.md).
Run the real Go agent on the client, with `AGENT_ALLOWED_ORIGINS` and `API_URL` set
to `https://vpn.mango.lab`.

- **Hosts entry:** `203.0.113.10 vpn.mango.lab`, on the client.
- **Trust Caddy's CA:** Lab 1 copies `caddy:/data/caddy/pki/authorities/local/root.crt`
  from `ubuntu-control`. Lab 2 takes Caddy's local root from `alb-ingress`, which
  also runs with `tls internal`.
- **Health:** `curl --fail https://vpn.mango.lab/health`.
- **Tunnel:** after the client connects, check the gateway:
  `docker compose exec vpn-gateway wg show` on `ubuntu-control` (Lab 1) or on
  `ec2-wg-gateway` (Lab 2).

For the role matrix, see Track B section B6.3 (ADMIN reaches all three zones,
STAFF misses admin, CLIENT reaches only client).

## 8. SSH access

- **Key:** `deploy/gns3/.local/lab_ed25519`, created once by `build-control-seed.sh`.
  The `.local/` directory (mode `0700`) also holds `lab-secrets.json`, `c1.env`,
  and `c2-gateway.env`. Never commit it.
- **User:** `lab`, key-only (`ssh_pwauth: false`), with passwordless sudo and the
  `docker` group.
- **Lab 1 `ubuntu-control`:** `ssh -i deploy/gns3/.local/lab_ed25519 lab@203.0.113.10`,
  reached from the host (`192.168.50.10`) through `host-client-lan.sh up` and
  `wan-router` `sg_wan`, or directly via its `virbr0` OOB DHCP address on the
  third NIC (`enp2s2`, shown in `/var/lib/libvirt/dnsmasq/virbr0.status`).
- **Lab 2 `ec2-wg-gateway`:** no public SSH path. Use its `virbr0` out-of-band
  DHCP address on the second NIC (`ens1`, see section 5.2).


## 10. Manual Track B reference

Use this section if you build Lab 1 by hand instead of with the provisioner. The
full walkthrough is in
[`02-track-b-gns3-mock-cloud.md`](../../docs/tutorial/02-track-b-gns3-mock-cloud.md).

1. **Wire the nodes** as in the Lab 1 address plan (NIC order matters; the setup
   scripts bind interfaces by position).
2. **WAN router:**
   `LAN_IFACE=eth0 WAN_IFACE=eth1 ENABLE_NAT=false sh deploy/gns3/setup-wan-router.sh`
3. **VPC router:**
   `TRANSIT_IFACE=eth0 ADMIN_IFACE=eth1 STAFF_IFACE=eth2 CLIENT_IFACE=eth3 sh deploy/gns3/setup-private-router.sh`
4. **Targets:** `ZONE=admin|staff|client sh deploy/gns3/setup-target-node.sh` on each.
5. **Control VM:** set the addresses and routes from section 3, then create `.env`
   with `npm run env:init` and start the stack:

   ```sh
   docker compose -f deploy/gns3/docker-compose.gns3.yml --env-file .env up -d --build
   ```

   Set `WG_SERVER_ENDPOINT=203.0.113.10:51820`, `CORS_ORIGIN=https://vpn.mango.lab`,
   and `VITE_API_URL=https://vpn.mango.lab`. Seed as in section 6, and seed the
   policies before connecting.

Manual builds do not get the return timer. Add it yourself, or the gateway's
return traffic goes through Docker NAT (see the Track B tutorial, section 2.1).

## 11. Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `GNS3 templates missing: ...` | Import the listed appliance templates (section 1), then rerun the provisioner. |
| `host-client-lan.sh` fails on `ip link show` | The `virbr-gns3` bridge does not exist. Create it, then start the `Cloud` node. |
| `Cannot add NIO on cloud "oob-nat": unable to open TAP device gns3tap0-0` | Re-provision with `--recreate` so `host-bridge` uses the bridged `mango-lan0` TAP instead of colliding with `oob-nat` on `gns3tap0-0`. |
| OOB SSH (`192.168.122.x`) or VM DNS times out with `[UFW BLOCK] IN=virbr0` | Ensure QEMU templates include `-global virtio-net-pci.csum=off -global virtio-net-pci.gso=off -global virtio-net-pci.guest_csum=off` (`--recreate`) and host `ufw` allows `virbr0`. |
| `rds-postgres` fails with `initdb: directory "/var/lib/postgresql/data" exists but is not empty` | Ensure `PGDATA=/var/lib/postgresql/data/pgdata` is set in the `rds-postgres` node environment (`provision-gns3-lab.py` sets this automatically). |
| `aws-localstack` exits with code `55` requiring `LOCALSTACK_AUTH_TOKEN` | Pin `"AWS Cloud Emulator (LocalStack)"` to `localstack/localstack:3.8.1` (`provision-gns3-lab.py` does this automatically). |
| `aws-loki` returns HTTP `503` right after boot | Wait ~15-30 seconds for warm-up before `http://10.50.30.31:3100/ready` returns HTTP `200`. |
| Two labs' nodes fight over `192.168.50.10` or `virbr-gns3` | Only one project can be running. Stop the other one. |
| `--recreate` removed work you wanted | Recreate deletes the project and its nodes. Export or back up first. |
| Probes to private targets succeed before connecting | Check that `wan-router` has no routes to `10.99/10.20/10.30` or `10.13.13.0/24`. |
